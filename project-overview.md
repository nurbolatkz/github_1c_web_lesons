1C + React Lessons — простой CRUD от 1С до production

1. Цель и границы курса

Практический курс для разработчиков 1С: создать простой справочник и документ, опубликовать HTTP-сервис базы, настроить FastAPI и SQL, собрать React-интерфейс с AI-агентом и выпустить приложение на Linux.

Учебный результат: пользователь входит на сайт, создаёт товар, выбирает его в заявке, сохраняет изменения и видит тот же результат в 1С. Разработчик понимает каждый переход, проверяет изменения локально в Windows и обновляет согласованную production-версию.

Бизнес-данные: справочник «Товары» и документ «Заявка на закупку» в 1С.

Web: React + TypeScript.

Backend: FastAPI; собственная SQL-база для пользователей и сессий.

Просмотр SQL: DB Browser for SQLite в учебной среде.

Разработка: Windows; React и FastAPI запускаются нативно.

Production web/backend: Linux, nginx, systemd и HTTPS.

Docker, SSO, Keycloak, сложное согласование и мультиорганизационные scopes в базовый курс не входят.

Публикация на GitHub Pages не является темой курса. Текущий сайт материалов: 1C + React Lessons.

Статус выбора авторизации: по запросу на простой и безопасный вариант рекомендованы серверные сессии с непрозрачным токеном в защищённой cookie. Это предложение для основного маршрута; отличие от ранее обсуждавшихся Bearer/JWT и OAuth2 объяснено ниже. Реальная реализация проекта этим документом не изменяется.

Товары и документы не дублируются в SQLite. SQL-база FastAPI — отдельное хранилище web-приложения, не прямое подключение к таблицам информационной базы 1С.

В этом упрощённом приложении пользователи web и простые права принадлежат FastAPI. Прежнюю схему KKT с профилями пользователей в 1С сюда не переносим. Учебные роли: «просмотр» и «редактирование»; все работают с одним учебным набором данных. FastAPI проверяет роль на каждом CRUD-запросе. 1С продолжает проверять бизнес-допустимость записи.

Браузер не получает пароль интеграционного пользователя и не обращается к 1С напрямую. Служебный аккаунт имеет только необходимые права.

5. Урок публикации 1С — обязательная практика

В основном Windows-маршруте выбираем IIS, чтобы не смешивать инструкции разных web-серверов. Перед написанием точных команд преподаватель фиксирует поддерживаемую версию платформы 1С, Windows/IIS и разрядность компонентов.

Ученик должен выполнить следующие действия:

Подготовить учебную базу и отдельного интеграционного пользователя.

Установить необходимые компоненты IIS и модуль расширения web-сервера 1С.

Создать HTTP-сервис в конфигурации: корневой URL, шаблоны и обработчики методов.

Обновить конфигурацию базы и опубликовать её на web-сервере.

Проверить включение нужного HTTP-сервиса в публикацию. Публикация web-клиента сама по себе не подтверждает работу API.

Проверить полный адрес, учётные данные и JSON-ответ независимым HTTP-клиентом.

Создать, прочитать, изменить и пометить запись; убедиться, что изменена именно учебная база.

Разобрать неверный адрес, отказ авторизации и исключение в обработчике по ответу и журналам.

Путь SQLite рассчитывается относительно рабочей директории приложения; урок фиксирует её. Для Linux используется постоянный путь вне каталога выпуска. При относительном пути нельзя незаметно создать новую пустую базу после запуска из другой папки.

Практика: изменить адрес 1С, получить ожидаемую ошибку связи, исправить настройку, перезапустить backend и повторить запрос. Отдельно сократить срок сессии в тестовой среде и проверить повторный вход.

Настройки backend применяются при загрузке конфигурации/перезапуске. Переменные Vite обычно встраиваются при сборке: изменение production .env без пересборки React не меняет уже собранный клиент. В VITE_* никогда не помещаются пароли и закрытые токены.

Для локального HTTP возможна отдельная development-настройка cookie без Secure; она не переносится в production. Более близкий к production вариант — локальный HTTPS. React использует dev proxy, чтобы браузер обращался к одному origin.

7. Рекомендуемая авторизация: серверная сессия

Для одного собственного React-приложения и FastAPI за одним доменом предлагается логин/пароль + случайный токен сессии в cookie + SQL-хранилище сессий. SSO и OAuth2-сервер для такого сценария не требуются.

Это сохраняет интересующий ученика предмет: токен, его хранение, срок действия и прекращение доступа. При этом не требуется отдельный цикл refresh JWT.

Поток входа

Пользователь отправляет логин и пароль на защищённый endpoint FastAPI.

Backend проверяет активность пользователя и хеш пароля, создаёт новый случайный токен и запись сессии.

В SQL хранится хеш токена; оригинал передаётся только в защищённой cookie. Токен не содержит профиль пользователя.

На каждом запросе FastAPI проверяет сессию, срок, отзыв, активность пользователя и актуальное право операции.

Logout отзывает сессию в SQL и очищает cookie. После истечения следующий запрос требует повторного входа.

В production cookie имеет HttpOnly, Secure, SameSite=Lax, Path=/ и не задаёт расширенный Domain. Можно использовать имя __Host-session. Срок и отзыв обеспечиваются сервером; удаление cookie само по себе не является отзывом. Основа — OWASP Session Management.

Пример стартовой политики курса: максимум 8 часов и 30 минут бездействия. Это предлагаемая настройка для обсуждения, а не универсальный стандарт. Сессия не становится бессрочной от постоянного продления. Смена пароля и блокировка пользователя прекращают старые сессии.

Условия безопасной реализации

Пароли хешируются готовой библиотекой с Argon2id; собственный алгоритм и обратимое хранение не используются. См. OWASP Password Storage.

Cookie-сессия требует CSRF-защиты для изменяющих запросов. Используется проверяемый CSRF-токен и проверка допустимого Origin; login также защищён от login CSRF. Одного SameSite недостаточно. См. OWASP CSRF Prevention.

Попытки входа ограничиваются по аккаунту и источнику; сообщения не раскрывают наличие логина. В production limiter не полагается на независимые счётчики нескольких workers.

Токен генерируется криптографическим генератором, например 32 случайных байта. Новая сессия создаётся после входа; не принимается навязанный клиентом идентификатор.

Секреты и токены не пишутся в URL, логи и localStorage. HttpOnly защищает чтение cookie JavaScript-кодом, но не устраняет XSS и не заменяет защиту приложения.

Middleware подписанной клиентской cookie не считается автоматически SQL-сессией. Для немедленного отзыва backend должен проверять серверную запись.

Чем это отличается от OAuth2/JWT

JWT — формат токена, cookie — механизм доставки, OAuth2 — протокол. Их нельзя использовать как взаимозаменяемые названия. Устаревший OAuth2 password grant не предлагается для нового production-решения: RFC 9700, раздел 2.4.

8. SQL-база и наглядная работа с таблицами

Под SQL browser в базовом маршруте понимается DB Browser for SQLite: программа для просмотра файла SQLite, его структуры и записей.

Таблица

Учебные поля

Что наблюдаем

users

id, username, password_hash, role, is_active, created_at

Создание пользователя, хеш вместо пароля, блокировка

sessions

id, user_id, token_hash, created_at, last_seen_at, expires_at, revoked_at

Вход, активность, окончание срока и выход

id записи сессии — несекретный идентификатор для диагностики, а не исходный токен. Отдельное внутреннее хранение данных CSRF определяется выбранной реализацией.

Практика в DB Browser:

Найти файл из DATABASE_URL и открыть учебную базу.

Посмотреть таблицы, типы, первичные и внешние ключи, уникальность логина и индексы.

Создать пользователя через предусмотренную команду приложения; увидеть запись в users.

Войти через UI; обновить просмотр sessions и найти новую строку.

Выполнить запрос; проверить обновление last_seen_at согласно реализации.

Выйти; увидеть revoked_at. Повтор старой сессии отклоняется.

Пройти тест истечения с коротким TTL и сопоставить SQL со статусом ответа API.

Пример запроса без секретов:

SELECT s.id, u.username, s.created_at, s.last_seen_at,
       s.expires_at, s.revoked_at
FROM sessions AS s
JOIN users AS u ON u.id = s.user_id
ORDER BY s.created_at DESC;

Приложение использует ORM и миграции; GUI служит для понимания данных, а не заменяет миграции ручным редактированием таблиц. DB Browser не показывает внутренние таблицы базы 1С.

SQLite подходит для локального обучения и ограниченного выпуска на одном сервере с умеренной записью. Файл находится на локальном диске, с ограниченными правами и резервным копированием. При росте конкурирующей записи или переходе к нескольким узлам выбирается серверная СУБД, например PostgreSQL; ограничения рассмотрены в документации SQLite. SQLite не объявляется универсальным production-выбором.

Рабочую базу с пользователями и сессиями не скачивают на ноутбуки для обычного урока; преподаватель использует учебный набор. Резервная копия SQLite создаётся согласованным способом, а не копированием одного активного файла без учёта WAL.

В запросе строки документа передаётся ID товара. Наименование для показа возвращается отдельно. Количество задаётся с согласованной точностью; даты и ведущие нули не теряются при преобразовании JSON.

UI по каждому объекту: список, просмотр и форма; Create/Edit могут использовать одну бизнес-форму. Для выбора товара в строку заявки — отдельный selector. Desktop: таблица; mobile: карточки там, где это сохраняет смысл. Состояния загрузки, пустого списка, 401, отказа прав и ошибок полей обязательны.

React хранит только состояние интерфейса и текущие данные формы; сервер определяет, разрешена ли операция. Пользователь «просмотр» не может записать данные и через прямой API-запрос.

10. Формат работы с AI и Git

Одна задача → одна ветка → небольшой diff → локальная проверка → PR → review → merge.

Пример задачи агенту:

Добавь редактирование товара по существующему API-контракту.
Сначала прочитай AGENTS.md, проверь ветку и текущие изменения.

Меняй только модуль products и его существующие API-функции.
Сохрани отдельные list/detail/form. Не меняй авторизацию и API 1С.

Поля: name и unit. ID и code не перегенерировать.
При ошибке сохранить ввод; после успеха показать ответ сервера.
Пользователю с правом просмотра не показывать редактирование.
Серверный отказ всё равно корректно обработать.

Покажи план, затем diff и результаты проверки в Windows.
Укажи, что не удалось проверить без работающей учебной 1С.

Команды изучаются в конкретных задачах: git status, diff, switch, pull, add, commit, push, fetch, merge; gh auth login, gh repo clone, gh pr create, gh pr diff, gh pr review, gh pr merge. Для запуска: npm scripts, Python venv и команды backend, реально определённые в проекте.

На уроке командной работы два ученика создают разные ветки, меняют пересекающийся фрагмент и разрешают конфликт по смыслу. Агент не выполняет широкую переработку проекта ради локального изменения формы.

Каждый урок содержит цель, исходное состояние, точные команды, ожидаемый результат, значимый отрицательный сценарий и небольшую самостоятельную задачу.

11. Проверки, которые сохраняем даже в простом проекте

Изменение через браузер читается обратно из той же учебной 1С.

Неверный товар или неположительное количество не записываются; ошибка не оставляет половину документа.

Нет сессии, срок истёк, выполнен logout или пользователь заблокирован — доступ закрыт.

Роль «просмотр» не выполняет запись через прямой запрос.

CSRF-проверка отклоняет неподтверждённые изменяющие запросы.

При ошибке или тайм-ауте 1С интерфейс не показывает ложный успех и сохраняет ввод.

Повтор POST с тем же ключом операции не создаёт дубль; защита выполняется в месте записи в 1С, а не только отключением кнопки.

При сохранении устаревшей версии документ не затирает чужое изменение. Проверка версии и запись в 1С атомарны.

Сбой после записи, но до ответа, не приводит к автоматическому повтору с новым ключом.

Обновление страницы, выход и mobile-сценарий работают ожидаемо.

Эти проверки разбираются на небольших примерах в уроке 16, без построения большого фреймворка. Исправления отображения не обрастают тестами, повторяющими CSS; запись и доступ проверяются по реальным последствиям.

12. Выпуск Windows → Linux

Локально

В Windows запустить React и FastAPI, проверить учебную публикацию 1С и путь SQL. Выполнить сценарий, изучить Network/Console и логи, собрать production React, отправить PR и пройти ревью.

Первый Linux-сервер

Подготовить пользователя сервиса, Python venv, зависимости, постоянный путь SQL, production-настройки и доступ к HTTP-сервису 1С. React и /api обслуживаются через один origin nginx. Настроить HTTPS, systemd, автозапуск, логи, резервное копирование SQL и проверку здоровья приложения.

В production cookie всегда защищена Secure. Наличие HTTPS на web-сайте не заменяет защиту внутреннего соединения FastAPI → 1С. На Linux нужно проверить фактическую сетевую доступность публикации, а не использовать localhost из Windows-примера.

Каждое обновление

Выбрать проверенный коммит/тег после merge и записать текущую версию для возврата.

Подготовить новый выпуск, установить зависимости и собрать React; не переносить Windows .venv и node_modules.

Подключить постоянные SQL и настройки; перед изменением схемы сделать резервную копию и применить миграции по плану.

При изменениях 1С обновить её конфигурацию/публикацию в совместимом порядке.

Переключить выпуск и перезапустить сервис. На одном сервере возможно короткое прерывание, которое заранее учитывается.

Проверить версию, логи, вход, сессию и CRUD через рабочий адрес. Запись в рабочую 1С выполняется по согласованному сценарию.

При отказе вернуть предыдущий выпуск. Откат кода не отменяет уже изменённую SQL-схему или документы 1С.

Каталог выпуска не содержит единственную копию рабочей SQLite. Иначе обновление может потерять пользователей и сессии. Production не редактируется вручную через AI; исправление снова проходит через ветку и локальную проверку.

13. Итоговая демонстрация

Ученик показывает:

Опубликованный HTTP-сервис и чтение товара отдельным запросом.

Параметры подключения через .env без демонстрации секретов.

Таблицы users и sessions в учебной SQL-базе.

Вход на сайте и появление сессии со сроком действия.

CRUD товара и заявки в браузере с проверкой результата в 1С.

Истечение сессии, повторный вход и logout с прекращением доступа.

Свой PR, обновлённую версию на Linux и проверку после выпуска.

После этого преподаватель может показать более крупный production-портал React + FastAPI + 1С как развитие той же схемы. Дополнительные типы документов, сложные роли, SSO, очереди и контейнеры рассматриваются отдельно после освоения простого приложения.
